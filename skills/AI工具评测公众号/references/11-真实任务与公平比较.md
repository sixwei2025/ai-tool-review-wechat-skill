# 真实任务与公平比较
先定义读者真正需要的交付，例如「把这份脱敏会议材料整理成能直接发送的纪要」，而非只让工具生成一段好看的文字。尽量使用可检查的原始材料，先确定验收条件，再看结果，避免随产物倒推评分。

## 方案最少记录什么
任务与目标用户；输入文件和完整指令；产品版本/套餐/地区/设备与测试日期；工具可用能力；验收条件；预算或停止条件；原始输出和修订输出；关键截图。
验收条件随任务定，不统一打十分：纪要看事实、遗漏、行动责任归属；演示稿看内容准确、结构、版式及可编辑性；表格看公式、数据完整和可复算；图片看需求遵循、文字、细节和修改能力。主观审美须注明判断标准，不包装成客观科学结论。

## 公平与效率
相同任务、原始材料、目标和基础指令；记录模型、联网、文件上传与付费权益差异。可先比相同输入的首轮，再比合理修订后的可用结果，两者分开写。不同产品需要不同交互时允许适配，但保存差异；不要要求界面不同的产品做完全相同的点击。
耗时从开始实际操作到可用结果，包括上传、等待、重试、检查和返工；只测生成时长就明确叫生成时长。没有人工基线不声称「省80%时间」；不要把不同口径的数据硬比。
区分实际支付、套餐标价和估算成本。估算写计算式、汇率/单位/假设，不把月费直接当单任务成本。
随机波动可能改变主结论时，视预算复测，保留所有次数与失败，不只挑最好的一次。只跑一次就不报告成功率，不用样本很少的结果作总体排名。
遇到登录、付费或授权阻碍时停下依赖该条件的步骤，继续可独立核验的资料工作。无须为了凑失败反复重试；预设预算耗尽后如实记录。

## 建议记录格式
测试ID / 任务 / 前提 / 完整输入 / 首轮产物 / 修订与次数 / 总耗时口径 / 直接成本 / 验收结果 / 失败影响 / 证据路径。
保留失败与中间结果，公开稿展示最能说明判断的部分。人工看过与脚本检查分开记录，不伪报人工审阅。
